# Astro 博客 Windows 桌面应用：功能分析与需求清单

分析日期：2026-10-09。本文用于确定产品范围与开发验收，不代表功能已经实现。

2026-10-10 调整：以 [ROADMAP.md](ROADMAP.md) 为当前实施顺序。AI 日报取消新增和专用编辑表单；源码移入 CodeMirror 主区三模式，属性保留右栏；增加外部编辑器、`npm run dev` 本地预览和用户选定的简洁统计。

2026-10-12：可配置的外部编辑器已实现，见 [EDITOR.md](EDITOR.md)。本文其余清单仍是历史规划，不代表当前交付。

## 1. 产品目标与范围

做一个面向现有 `promefire/Astro_Blog` 的 Windows 博客工作台，完成“同步文章 → 写作 → 保存草稿 → 预览 → 发布 → 查看结果”。文章继续使用仓库中的 Markdown/MDX 文件，发布继续使用 GitHub 推送后触发服务器部署的现有方式。

首版以单人、单个 Astro 博客为主。多台电脑可以各自克隆同一仓库，通过显式同步和发布同步接续写作。不承诺实时协同，也不增加独立的笔记数据库。

暂缓：语雀替代平台、知识库问答/RAG、Reviva 集成、教程站统一管理、多用户权限、服务器控制面板和日报调度管理。DeepSeek 辅助写作可独立作为第二阶段功能。

## 2. HexoHub 已有能力与适用边界

依据 README、发布记录及源码分析，未安装运行其 Windows 安装包。分析源码提交：`bb39de860d529d0535ffdf50e4631675c508b1c4`；本次查看的发布页列出 v3.7.0。

| 模块 | 文档或源码中可核实的能力 | 对 Astro 应用的启发 |
| --- | --- | --- |
| 项目管理 | 选择、验证 Hexo 项目，新建 Hexo 项目，保存项目路径 | 首版改为打开/克隆现有 Astro 仓库，不必加入建站向导 |
| 文章管理 | 新建、列表、编辑、删除；搜索、分类/标签筛选、排序和分页；批量删除及修改分类/标签 | 可以保留主要交互，改用 Astro collection 和字段 |
| 新建文章 | 标题、标签、分类、摘要、模板、自定义 frontmatter 字段 | 仅新建普通文章草稿；标题必填、单分类，AI 日报不新增 |
| 编辑预览 | Markdown 源码编辑、编辑/预览切换、左右分栏、全屏；基础格式操作；静态和本地站点预览 | 首版采用源码+预览；完整 Typora 式即时渲染另行开发 |
| 图片 | 拖拽图片复制到文章资源目录，插入 Hexo 图片标签 | 改为项目可构建的 Markdown 图片路径，不能沿用 Hexo 标签 |
| 站点操作 | clean、generate、server、deploy；自定义命令；执行反馈和日志 | 对应项目的 dev、build、preview 脚本和现有 Git 发布链路 |
| Git | 设置仓库、分支、提交身份，暂存、提交、推送 | 必须补齐拉取合并、变更选择、冲突处理和发布状态 |
| AI | 灵感、文章分析、选中文本改写/润色/扩写/翻译、模仿写作；DeepSeek 等接口配置 | 可选辅助写作，不等同于基于全站笔记的检索问答 |
| 设置与概览 | 自动保存间隔、面板布局、背景、语言、更新检查、标签云、发文统计 | 基础编辑偏好优先，装饰与统计后置 |

需要特别区分的事实：

- HexoHub 的两个编辑模式分别是“切换编辑/预览”和“左右分栏”；主编辑器使用文本输入组件。不能据此认为已有完整所见即所得编辑器。
- 本次审阅的 `pushToRemote` 执行配置、`git add .`、提交和推送，未在这段流程中执行 fetch/merge。你的服务器会自动提交日报，桌面端不能直接复制这段发布逻辑。
- Hexo 项目路径、`_config.yml`、`scaffolds`、图片标签、日期字段、默认预览地址均带有框架假设。适配 Astro 涉及内容、资源、预览、命令和 Git 工作流。

## 3. 当前博客需要适配的数据与行为

已通过 GitHub 连接读取当前仓库的内容定义、配置和相关工具函数。

| 内容 | 目录 | 已核实的字段/行为 |
| --- | --- | --- |
| 普通文章 `post` | `src/contents/post`，支持 `.md`、`.mdx` | 必填 `title`、`published`；可选 `draft`、`description`、`cover`、`tags`、`category`、`author`、`sourceLink`、`licenseName`、`licenseUrl`、`password`、`top` |
| AI 日报 `aiDaily` | `src/contents/ai-daily`，支持 `.md` | 必填 `title`、`published`、`summary`；数组 `highlights`、`tools`、`tags` 默认空数组；目前没有声明 `draft` 字段 |
| 特殊页面 `specs` | `src/contents/specs` | 独立 collection，首版可以后置管理 |
| 站点配置 | `yukina.config.ts`、`astro.config.mjs` | 使用 TS/JS 配置；不能当成 Hexo YAML 配置重写 |
| 命令 | `package.json` | 已有 `dev`、`build`、`preview`；dev/build 前有生成音乐列表脚本；声明 pnpm 包管理器，应允许配置并与部署环境一致 |
| URL | `yukina.config.ts`、`src/utils/hash.ts` | 当前配置 `PINYIN`，支持 RAW/HASH/PINYIN；文章 URL 应依据项目路由和转换规则生成 |
| 草稿 | `src/utils/content.ts` | 普通文章列表、归档、标签、分类在生产环境过滤 `draft: true`；最终验收还需覆盖直接路由、RSS、搜索索引 |

这里的 `published` 是日期字段，不能替换成 Hexo 的 `date`。`category` 是一个字符串，不能保存成 Hexo 多分类数组。`top` 是整数，不能未经转换保存为布尔开关。AI 日报保留现有字段读取，不提供新增或专用编辑表单，不套用普通文章的草稿控制。

部署状态接入前需核实真实部署入口。仓库中读到 `.github/workflowdeploy.yml`，仅看到此文件不能证明当前自动部署由 GitHub Actions 执行；桌面应用应沿用并识别真实的自动部署方式。

## 5. 建议界面

主导航保持简单：

1. **文章**：普通文章、草稿、AI 日报；列表、搜索、筛选。
2. **编辑**：正文与预览位于中间，右侧为文章属性、大纲、资源；顶端提供保存、预览、发布。
3. **发布与同步**：远端更新、待提交差异、提交/推送记录、部署反馈。
4. **设置**：项目、Git、编辑器、预览构建；AI 放在可选设置内。

状态栏始终提供当前项目/分支、保存状态、同步状态、预览服务状态。首版不必把统计仪表盘作为应用首页。

## 6. 发布流程与状态规则

推荐流程：保存正文和属性 → 选择文章及依赖资源 → 校验字段并形成本地提交 → fetch/merge → 对合并后的代码构建 → push → 现有部署系统执行 → 获取部署反馈或标记待确认。

- 未选入提交的本地改动必须保留；如妨碍合并，提示先处理，不能自动丢弃。程序采用专用工作副本时也应保留恢复记录。
- 合并冲突时停止推送。用户解决并确认后，重新构建，再继续发布。
- 推送被拒绝时重新获取远端并合并，设置有限重试次数；冲突不自动任选一边。发生合并后要重新构建。
- “已发布”的版本应对应最后一次确认成功部署的 commit；没有回执则显示“已推送，部署待确认”。
- 普通文章发布是 draft 解除后进入上述流程；撤回是设为草稿再走同样流程。撤回不自动删除 Git 历史。
- 当前 AI 日报 schema 没有 draft。若以后要日报暂存/撤回，应同步修改网站的数据定义及展示规则，单加桌面开关无效。
- 当前 published 日期字段本身不构成定时发布机制，首版不声称可以设置未来时间自动上线。

## 7. 首版验收场景

| 场景 | 通过条件 |
| --- | --- |
| 首次使用 | 选本地目录或克隆仓库后能列出文章与日报；缺少 Git/Node/依赖有明确提示 |
| 完整写作发布 | 新建普通文章、编辑属性、粘贴图片、预览、发布后，GitHub 包含文章和资源，部署确认后线上可访问 |
| 保存草稿 | 自动保存不推送；draft 普通文章在本地可预览，在生产页面、RSS和搜索等入口按站点规则排除 |
| 源文件兼容 | 已有文章读写后自定义字段、MDX import/组件、中文文件名均不损坏 |
| 日报并发提交 | 服务器新增日报后，桌面端发布普通文章成功包含双方提交，不覆盖日报 |
| 同文冲突 | 两台电脑修改同一段正文时，冲突可识别且阻止推送，原始双方内容可恢复 |
| 断网和认证失败 | 保存仍可用，文章和提交不丢失；恢复连接后能重试，未错误标记上线 |
| 依赖资源与部署 | 本地图片在实际生产构建可见；push 成功但部署失败时，界面分别呈现两种结果 |
| 外部修改 | 外部编辑器修改正在编辑的文件时，有差异提示，不静默覆盖 |
| Windows 安装 | 中文路径及带空格路径下可安装、打开仓库、运行预览；升级后文章仍完整 |

## 8. 实现取舍

建议先实现当前博客的固定适配器，再考虑通用 Astro 博客支持。采用 HexoHub 的操作结构和部分组件可减少交互工作；项目识别、内容模型、资源、路由、预览命令和发布流程仍需重新适配。

桌面壳可在 Tauri/Electron 中选择一个维护。源码同时包含两套桌面适配，并不要求新应用也保留两套。选型不影响本清单的功能定义。

如果复用 HexoHub 源码，应保留其 MIT 许可证要求的版权与许可声明。是否 fork 二次开发，或新项目复用局部组件，应在实现阶段依据代码维护成本决定。
